the gap this closes

Most student matching engines fake the hard part

Linear scans dressed up as "order books," queues that lose time priority, and no durable record of what happened — this design replaces all three with the data structures a real venue would use.

Typical prior models

  • Scans a flat list of orders for every match — O(n) per trade
  • Price levels stored unordered, so time priority breaks under load
  • Cancel/modify requires searching the whole book by ID
  • No persistent record — history disappears when the process exits
  • In-memory only: a crash loses the entire book instantly

This engine

  • Max-heap bids / min-heap asks — best price is always O(1) to read
  • Per-price doubly linked FIFO queues preserve strict arrival order
  • Hash-indexed order IDs → direct pointer, O(1) cancel/modify
  • Every accept, cancel and trade appended to an event log
  • SQLite in WAL mode durably persists state without blocking reads

core implementation

Five structures, one matching loop

Everything below is implemented in pure C and sits behind the Streamlit interface as the engine's actual decision logic.

01 · heaps

Bid & ask priority queues

A max-heap keeps the highest bid at the root; a min-heap keeps the lowest ask at the root — both rebalance in O(log n) on insert or remove.

02 · linked lists

Per-price FIFO queues

Every price level holds its own doubly linked list, so two orders at the same price always fill in the order they arrived.

03 · matching loop

Price-time crossing

While best bid ≥ best ask, the loop pulls the front order from each queue, fills the smaller quantity, and emits a trade.

04 · hash index

Order ID lookup

A hash table maps every order ID straight to its linked-list node, so cancels and modifications never scan the book.

05 · event log

Durable audit trail

Accepts, cancels and trades are appended to a log and mirrored into SQLite (WAL mode) for replay and verification.

06 · interface

Streamlit control room

A Python/Streamlit layer submits orders to the C core and renders book depth, the trade tape and live performance counters.

submit_order()→push to heap + FIFO queue→while best_bid ≥ best_ask: match & reduce qty→emit trade→append to event log / SQLite WAL

order handling

Correct behaviour, not just correct output

Limit orders, market orders, cancellations and partial fills are each handled as distinct code paths against the same book, using C structs and dynamic memory rather than fixed-size arrays.

limit

Rests until matched

Posts to the heap and FIFO queue at its price if it can't fill immediately.

market

Fills against best price

Walks the opposite book until filled or the book is exhausted.

cancel / modify

O(1) via the index

The hash index jumps straight to the node — no scan of the book.
